# 华夏史网 · ChronoGraph China

> 二十四史人物关系图谱与史料对勘引擎 —— 把「谁和谁有什么关系」变成可点击、可溯源、可对勘的知识网络。

一个纯静态的数字人文应用：Canvas 全息图谱 + 语义级缩放 + 单年历史截面 + 六度寻路 +
文白对照读本。所有史实内容都绑定文言原文引文，注疏与笔记按可信度分级标注。

---

## 一、为什么不是又一个「历史人物百科」

三条硬约束决定了它和同类产品的区别：

1. **零历史幻觉**。每一条生平、每一则轶事、每一条关系，都挂着一个 `HistoricalCitation`，
   含书名、卷次篇名、文言原文、白话译文、史源分级。演义情节不进正史，野史必须标
   `literary_anecdotal`。自检工具能证明「伪造引文必被拒」这条防线真的生效。
2. **关系是有时间轴的**。人与人的关系不是静态标签：李斯与韩非从同门到构陷，刘邦与项羽
   从结义到死敌。`temporalPhases` 状态机让连线在单年截面上改变颜色与语义。
3. **史料是允许冲突的**。同一件事，《旧唐书》与《资治通鉴考异》各执一词时，界面呈现
   「罗生门」左右对勘，而不是替读者选一个。

### 两级考据：为什么有一半人没有原文引证

要把图谱从两百人铺到四五百人、再往六百人走，就绕不开一个硬约束：**原文只能人工录入**。
维基文库与 ctext 在本机均不可达（前者域名不通，后者的 API 要授权、网页有 Cloudflare 人机验证），
所以每一句文言都是手打进去的。规模一上来，记错一个字就是伪造引文——那比少几个人严重得多。

于是人物分成两档，并且把档位写在脸上：

| 档位 | 人数 | 要求 |
| --- | --- | --- |
| **考据级** `annotationLevel: 'full'` | 97 | 本传原文 ≥ 2 段（文白对照）· 轶事 ≥ 1 则（附原文）· 史官评语原话 · 年表 ≥ 3 条 |
| **简目级** `annotationLevel: 'brief'` | 805 | 姓名 · 字号 · 朝代 · 阵营 · 生卒 · 籍贯经纬 · 职官 · 生平骨架 · 年表 ≥ 2 条 · **本传卷次篇名** |

简目级**不写原文**，只著录「此人的传在《史记》哪一卷」。这是可核查的元数据，不是引文，
所以读者能自己去翻检，而不必相信我默写的句子。档案页对简目人物会显示醒目的「简目」档位声明，
关系的书证栏也从「直接书证」改为「此关系见于何卷」。

这是**显式降级，不是静默放水**：校验脚本、编译脚本和前端都按档位分别设限，
两档的边界写在 `src/types/history.ts` 的 `annotationLevel` 注释里。
若日后拿到可用的原文数据源，简目人物可以逐批升格为考据级，升格条件即上表右列。

### 第二批扩容：把楚汉与隋唐补到与三国同密度

第一批是「三国厚、两头薄」：三国 155 人，楚汉 36 人，隋唐 25 人。点开首页，三个分片并排，
后两段稀得像是占位。第二批就干一件事——把楚汉补到 143 人、隋唐补到 146 人，
让三段密度基本持平。

做法是**只写简目，不碰考据级**。新增 289 人全部落在 `annotationLevel: 'brief'`，
不录文言原文（原文源在本机不可达，手打默写就是伪造引文的风险），
只著录「此人的传在《史记》卷几」「在《旧唐书》卷几」——这是可核查的元数据。
考据级 97 人一个字没改，原有书证不受影响。

代价是明摆着的：全站平均年表密度从 4.0 条/人降到 3.1 条/人。这是扩容的必然代价，
所以简目档的下限（年表 ≥ 2 条）由编译脚本硬拦，不能靠凑数条目蒙混。

补的过程中有三件事值得记下来，都是自己绊自己：

1. **孤立节点。** 新人一次性入库后，楚汉分片冒出 **106 个孤点**——节点在画布上飘着，
   一根线都没有，等于把图谱退化成名录。于是每批新人必配一份 `edges-brief.ts`，
   按「君臣 / 姻亲 / 师承 / 政敌 / 沙场对手」五类逐人连线，连完再跑度数统计复测。
   楚汉补完仍余一个（韩安国），追了三条边才归零。现在三片孤点数均为 0。
2. **id 撞车三次。** 三个分片共用一个 `person_*` 命名空间，跨代重名直接触发
   「已在其他分片出现，已跳过」——人不声不响地少一个。查到三处：
   楚汉栗姬 vs 隋唐李勣（`li_ji`）、三国陆绩 vs 隋唐陆贽（`lu_zhi`）、
   三国李严 vs 唐武宗李炎（`li_yan`）。一律加朝代后缀消歧（`li_ji_han` / `lu_zhi_tang` / `li_yan_tang`）。
3. **一条时序倒置的边被审计抓了。** 吴道子与阎立本被我顺手写成「师承」并系年 700→673，
   而阎立本卒于 673 年、吴道子约生于 685 年——两人根本不同世。
   改成不系年的「画脉相承」，并在边注里写明「二人不相及，非有亲授」。
   这类错误的危险在于读起来很顺，只有把生卒年拉出来对一遍才露馅。

### 第三批扩容：补先秦与两晋南北朝，越过六百人

第二批补完是 444 人，但时间轴上还有两处空白：**最左端**（西周至战国，一格都没有）和
**三国与隋唐之间的三百年**（两晋十六国南北朝，整段缺失）。这两处不补，图谱就不是「华夏史」，
而是「三个我比较熟的断代」。第三批就是补这两处：先秦 102 人、两晋南北朝 95 人，全站 444 → **642 人**。

这一批遇到的坑与上一批不同，记四条：

1. **生年不能倒推。** 三代人物生卒多不可考，《史记》诸世家只纪世次、不纪年寿。
   一开始按「在位年数」倒推姬昌、吕尚的生年，被校验脚本当场拦下（`birthYear 越界：-1152`）。
   正确的做法不是放宽 `yearRange` 去迁就，而是**删掉生年、标 `uncertain: true`**，
   并在档案页注明「文王生年史无明文，旧说寿九十七出于纬书推算」。
   同理，吕尚只写「盖太公之卒百有余年」，不写生年——这是《史记》的原话，不是我的推算。
2. **并称不等于交集。** 先秦人物相隔数代、素未谋面者极多（老子与庄子、管仲与晏婴、
   李牧与项燕），若强作「君臣」「师承」就是虚构。凡此类一律走 `literary_bosom` 或
   `political_ally`，且 summary 里明写「二人不相及」「史传未载往还」，
   只论学脉与事功上的并称。两晋南北朝同理：葛洪与陶弘景、鸠摩罗什与法显、顾恺之与嵇康，
   这三条边都带这句声明。
3. **id 撞车又踩两次，而且这次是「后来者让位」。** 刘勰撞三国的刘协（汉献帝）、
   王献之撞隋唐的王仙芝。上一批的处理是「先建者保留、后建者改名」，
   这次照旧：`liu_xie_wenxin`、`wang_xianzhi_shu`。
   撞车不报错、只告警，丢的是后建分片的人——这类静默丢人在加到第五个分片时最容易漏看，
   所以每加一片必先跑一次全库 id 比对，不能等 `build-seed` 的告警。
4. **阵营泳道要防「跨代误并」。** `FACTION_RULES` 是按正则匹配阵营名的，
   新片用了「文人」「降将」这种极常见的词，会被唐段的「山东士族与文人」「李唐皇室」抢走，
   在画布上把两晋的陶渊明挂到唐代的泳道里去。改成「文苑」「侯景集团」并把新规则前置，
   才各归其位。**新朝代的阵营名越通用，越要靠前精确匹配。**

**这一批还量出了一件比加人更要紧的事：力导向布局已到硬天花板。**
为此专门写了 `scripts/bench-layout.mjs`（只量布局、不量渲染），在 642 人基准上实测到
3,210 人需要 97.6 秒——再加下去首页就是一分半白屏。**卡住的不是数据量，是算法。**
于是紧接着做了第四批：把斥力从两两精确的 O(n²) 换成 Barnes-Hut 四叉树 O(n log n)，
同一档从 97.6 秒降到 2.5 秒，并用距离相关性 r=0.996 证明图没变。
详见第八节「性能基线」。**第四批只换引擎、不加人**——加人留给了第五批。

### 第五批扩容：补五代十国与新莽更始，八片齐备

第四批换完引擎后，时间轴上还留着两段空白，而且性质不同：

* **五代十国（907–960）**：夹在唐亡与陈桥兵变之间的五十三年，此前一格都没有。
  这是「五十三年的真空带」，读者从唐末一点就跳到宋朝，中间像被剪掉了一段。
* **新莽更始（9–25）**：更麻烦的地方在于，它跨着整条东汉开国的脊梁——
  光武帝与云台二十八将原本一个都不在库里。此前图谱里汉光武是不存在的，
  「光武中兴」只能靠三国分片里的后人追述间接提及。

两片合计 92 人（45 + 47），全站 785 → **877 人 / 1,397 边**。两片**全部为简目级**，
不录原文，只著录「此人的传在《后汉书》卷几」。新片的权重与边全部走 `src/data/_helpers.ts`
的 `pb()` / `rb()` 构造器，不手写 JSON。

这一批的坑与前三批又不一样，记五条：

1. **六处 id 撞车全部是「同音不同字」，暴露了拼音 id 的系统性缺陷。** 五代片一入库就撞了六个人：
   郭威 / 郭隗（都是 `guo_wei`）、李璟 / 李靖（`li_jing`）、李煜 / 李豫（`li_yu`）、
   王建 / 王翦（`wang_jian`）、刘龑 / 刘晏（`liu_yan`）、黄筌 / 黄权（`huang_quan`）。
   前代人物按「先建者保留」不动，五代六位加 `_fd` 后缀。**注意这不是「重名」，是同音**——
   「隗」读 wěi、「璟」读 jǐng，拼音与「威」「靖」完全相同。
   只要 id 用拼音，这类冲突就是必然的，**而不是偶发事故**；所以每加一片必须先做全库 id 求交集，
   不能等 `build-seed` 告警——它只告警、不报错，丢的是后建分片的人。
2. **但有一处撞车不是同音，是真人重复，后缀救不了。** `person_li_keyong`（李克用）
   被五代片当成开国主角重写了一遍，而隋唐片早就收了他——李克用死于 908 年，
   本来就是唐末人物，归隋唐并不错。这种情况**改 id 只会留下两个李克用**，
   正解是整块删掉五代那段并重写其边。判断标准一句话：
   先问「这是改这个人的信息，还是决定这个人在哪一片」。
3. **新莽片有两组「同姓名人分属敌对阵营」，是这批里最危险的。** 绿林领袖王匡与新室太师王匡是两个人；
   绿林王凤与王莽的叔父王凤也是两个人。四个人的字、籍贯、官职全都不同，但名字一模一样——
   `person_wang_kuang` 只能给一个人，另一人必须显式写成 `wang_kuang_lvlin`。
   这比「郭威撞郭隗」恶劣得多：隗与威至少字不同，王匡与王匡连字形都分不开。
   一旦并成一个节点，图谱会把「反莽起兵的人」和「替王莽守洛阳的人」画成同一个圆点，
   而这两拨人在战场上是对面站着的。**凡同姓同名的敌对双方，必须先分立 id，再连边。**
4. **阵营正则前缀又误伤了三个别代阵营，这次纯粹是「词太短」。** 新片起初用了
   「南阳」「齐地」「并州」三个短词，结果 `/^南阳/` 把三国的「南阳何氏」也吞了、
   `/^齐地/` 吞了楚汉的「齐地群雄」、`/^并州/` 吞了三国的「并州军事集团」与隋唐的「并州士族」。
   界面上的表现是：三国的何氏忽然出现在新莽的泳道里，而新莽本地人反倒分了家。
   修法不是调顺序，而是**把阵营名写全**——「南阳豪族」「齐地张步」「并州卢芳」，
   十七条新规则全部锚定到完整阵营名，再跑一遍全库 `factionOrClan` 交叉比对，
   打印「十七条规则均只命中本片阵营」才算过。第三批记下的教训是「规则要前置」，
   这一批补上后半句：**前置只能解决「被抢」，写全才能解决「互抢」。**
5. **权重平方标定会把「看着不低」的数值打成低权重。** 编译期有一条单调标定
   `calibrated = round(100 * (raw/100)²)`，用意是拉开头部差距；副作用是 34 → 12、42 → 18。
   新莽片按「主角 100、骨干 60、配角 34」的直觉写下来，结果单片视图只显示 17/47 人——
   因为中观档的门槛是权重 ≥ 40，而那 30 人全落在 12–18。**这不是渲染 bug**：
   定位时一度以为是投影裁掉了节点，临时把 `positioned / visible / offCount / bounds`
   打到 `window.__gdbg` 上才排掉嫌疑（`offCount: 0`，`bounds` 与坐标范围逐位相等）。
   要给某人在中观档可见，原始权重至少要写到 **63**（63² ≈ 40）。
   同一套分层阈值在别的片也一样生效：先秦 45/102、隋唐 72/146 都低于半数，
   **「视口只有一部分人」是 LOD 分层，不是丢数据**——判据是切到微观档后总数对不对。
6. **简目档也要求 `structuredBiography` 至少两段。** 校验脚本对简目不要求文言原文，
   但要求两段白话生平骨架——这是「简目不等于只有一行字」的底线。
   新片首次审计就因 38 人缺骨架被拦下（`简目人物也需至少填写一段 structuredBiography`），
   补写后 877 人全过。**这条门槛故意留在编译期**，就是为了逼作者在入库时把人物想清楚，
   而不是先占坑后补内容。

### 第六批扩容：补辽金西夏，不再只有半边图

八片齐备之后按朝代重新数了一遍人头，发现一个此前被总量掩盖的凹陷：宋元明清片 143 人里，
宋 64、清 29、明 25、元 16，而**辽、金、西夏三家合计只有 9 人**——辽 3、西夏 1、金 5。
可这三家与赵宋并立三百余年，澶渊之盟、靖康之变、采石之战、蔡州之围，每一件都是南北双方共同造成的。
总量上「八片 877 人」看着很满，把分片内部拆开看，才暴露出这片是个**半边图**：
澶渊之盟画得出寇准，画不出对面帐里中弩的萧挞凛；靖康之变画得出一群北宋文臣，
画不出押着二帝北去的人。**总量达标不等于分布达标，扩容前必须先按片内朝代重新数一遍人头。**

这一批补 25 人（辽 8 · 金 9 · 西夏 5 · 宋方 3），全站 877 → **902 人 / 1,439 边**，
宋元明清片 143 → 168 人。全部简目档，传目著录于《辽史》《金史》《宋史》夏国传。
五条经验：

1. **补人之前先问「这场戏缺的是谁」，不是「还有谁没写」。** 辽金西夏缺的不是凑数的名字，
   是**对手方**——澶渊缺萧挞凛（中弩促成和议）、靖康缺宗望宗翰（俘二帝的主帅）、
   采石缺虞允文（宋方督战者）、蔡州缺完颜守绪与孟珙（城破与合围）。
   先列事件再列人物，每个人的边都直接挂在已有的宋方节点上，图立即从「两簇」变成「一张网」。
2. **复姓 id 的拆法要跟着库里的既有约定走，不跟着拼音习惯走。** 耶律、完颜一律拆成
   `ye_lu_*` / `wan_yan_*`（与既有 `ye_lu_abaoji` / `wan_yan_aguda` 一致），
   而不是写成 `yelv_*` / `wanyan_*`——id 的可读性是给后续维护者看的，
   前后不一致比不拆还糟。
3. **《辽史》里的人不叫这个名字。** 韩德让在《辽史》本传题作「耶律隆运」（赐姓改名），
   耶律大石附于天祚帝本纪之末、不别立「西辽本纪」。**传目必须照原书卷次写**，
   按「韩德让传」去找会扑空；同时把通行名留在 `name`、赐名放进别名字段，两头都能检索。
4. **简目档也得有庙号字段。** 耶律隆绪、完颜亶这些本名，反不如「辽圣宗」「金熙宗」通行，
   读者搜庙号必须能命中。但「号」（应天太后）与「庙号」（圣宗）是两套东西，
   把庙号塞进 `hao` 会让档案页把它显示成别号——所以给 `pb()` 补了 `miao` / `nian`
   两个可选字段，与考据档 `p()` 同口径映射到 `templeName` / `eraNames`。
   **构造器字段不够用时扩构造器，不要把语义塞进错误的字段。**
5. **阵营前缀又被验证了一次：写全才能防互抢。** 辽金这批新阵营名（辽室/辽将门/辽汉臣/
   西夏/金室/金宗室/金将门/金文苑）若图省事写成 `/^辽/`，实测会同时抢走明代「辽东边将」
   与三国「辽东公孙氏」——一个词把三家分片的人拉进辽的泳道。
   八条前缀逐个写全后跑交叉比对，全库以「辽」「金」开头的九个阵营名各归其位。

这一批还顺手把分片验收脚本做成了通用的：`verify-shard.mjs <分片简称>`，
出整库首屏 / 单片 / 泳道三张图，人数断言自动从 manifest 读，以后每加一片一条命令即可。

### 第七批扩容：元明清补齐，卷次逐条联网核验

辽金西夏补齐后按片内朝代再数一遍，凹陷挪到了元代：元 16 人里缺席的恰是一串关键角色——
蒙哥、旭烈兀、刘秉忠、许衡、阿合马、张弘范、王保保一个都不在；明代的杨溥杨荣、俞大猷、

全站 902 → **952 人 / 1,510 边**，宋元明清片 168 → 218 人。全部简目档，
卷次**逐条联网核验后才写**，过程中纠了三处险些入库的错：

1. **三家三卷并作一卷。** 张廷玉、傅恒、福康安初稿并记《清史稿》卷 288；
   核验后张廷玉实为卷 288（列传七十五，与鄂尔泰同卷）、傅恒卷 301（列传八十八）、

2. **《元史》无专传者要写明理由。** 旭烈兀、蒙哥事迹散见本纪（卷 3 宪宗）与诸王表，

   不替《元史》补一个它自己没写的籍贯。

边的纪律同前（已有边不重连、不相及者不硬连、同传并置须写明非交往）：
新增 56 条，如张弘范—文天祥（五坡岭）、张弘范—张世杰（崖山）、许衡—阿合马（政敌）、

#### 第二轮补图：三个被自己搞错的判断

第一轮只收到 47 张，复盘时发现三处系统性错误，修正后增至 59 张：

1. **把「慢」当成了「无」。** 探测超时写死 15 秒，而馆藏像轴原件常在 4000×6000 级，
   经代理回源缩放往往超过 15 秒，于是《明人画张良像轴》这样的真迹被判成「不存在」。
   现改为 60 秒 + 退避重试，「超时」与「404」严格分开。
2. **全角括号写成了半角。** 《說唐演義全傳》绣像一族的题名用全角「（）」，
   候选题名表用半角「()」，杨广、李靖因此整批漏收。补上后即得两人。
3. **对「白底」的判断过严。** 三国绣像中有几张经后人描清、纸色与刀痕不存，
   第一轮一律判作「现代白描重绘」。复核其 Commons 著录后改判：
   荀彧一帧明载出自**東京大學東洋文化研究所藏雍正十二年（1734）刊本**，刀痕墨聚俱在；
   周瑜、鲁肃、陆逊、法正、马超、姜维、曹植七帧同属清刊系统，但图档确经描清，

#### 第三轮：这批人为什么没配上图（一次失败的记录）

第二批扩容了 289 人，按理该再跑一轮检索。**这一轮一张也没配上**，原因不是没找，是找不到入口：

| 通路 | 状态 |
| --- | --- |
| `commons.wikimedia.org/w/api.php`（Commons 检索 API） | 连接超时，空响应 |
| `zh.wikipedia.org/w/api.php`（维基百科 API） | 同上 |
| `r.jina.ai` 文本代理 | 不通 |
| `api.allorigins.win` / `api.codetabs.com` 跨域代理 | 不通 |
| `thumb.wikimedia.org` 直取缩略图 | 超时 |
| **`images.weserv.nl` 图片回源代理** | **可用**（本轮唯一的通路） |

问题在于 weserv 只能取**已知文件名**的图，不能检索。没有检索就只能猜文件名，
而 Commons 的文件名是自由题名——`Wu Zetian.jpg` 不存在，真实文件可能叫
「Empress Wu Zetian from an 18th century album…」之类。所以做了两次枚举，都是零命中：

1. **直猜西名**：对权重最高的 10 位无图人物（武则天、刘彻、吕雉、长孙氏、陈胜、霍去病、
   独孤伽罗、李斯、卫青、安禄山）试 `<西名>.jpg|png` 25 个候选，**命中 0**；
2. **顺着册页猜页题**：本站已收的 59 张里有两种成套册页——费城艺术博物馆《Portraits of Famous Men》
   （页题一律 `Portraits of Famous Men - <西名>.jpg`）与臺北故宮《歷代聖賢半身像》冊
   （页题一律 `歷代聖賢半身像 冊 <中文名> (<拼音>).png`）。同册页题是规律的，于是对 20 位人物
   枚举 102 个页题、含威妥玛拼音变体（`Li Ssu`、`Huo Ch'ü-ping`、`Wu Tse-t'ien`），**命中 0**——
   说明这两册根本没收录这批人，不是题名猜错。

此事要连着说清：上一轮的 59 张是**逐个比定**出来的，不是靠命名规律批量捞的。
所以这批 385 位不是「暂时没轮到」，而是在当前网络条件下**确实取不到**。
等检索通路恢复（`api.php` 可达即可），`scripts/portraits/probe.mjs` 能直接复用，
届时按「比对题名 → 落缩略图 → 人眼过一遍 → 写入 catalog」四步走，命中多少算多少。

这也是为什么画像覆盖率写着 100%、却仍要在此处说明「真图只有 103 张」：
**有图**与**有真图**是两件事，混着说就是骗人。

#### 第四轮（随第七批扩容）：元明清 47 人候选，收 24 张

第七批扩容补齐元、明、清三代后，对 47 位无图人物重开检索。两条教训先记下：

1. **`Special:FilePath` 经 weserv 代理已不可用。** 纯中文/拼音裸题名走
   `Special:FilePath` 会限流到 10–14 秒一探然后 404，50 人 × 28 候选要跑数小时且零命中。
   改走 **MD5 哈希直链**：Commons 缩略图路径可由文件名自行推算
   （`thumb/{h[0]}/{h[0:2]}/{名}/{宽}px-{名}`，h 为文件名的 MD5），
   `scripts/portraits/fetch-ymq.mjs` 据此直取 500px 缩略图再过 weserv，32 分钟跑完 47 人。
2. **检索 API 会报已删文件，存在性必须用 `prop=imageinfo` 核验。**
   《元代帝后半身像》册的蒙哥一叶已于 2014 年被 Commons 删除（疑为现代仿作），
   搜索结果里却还在；真收的是单件《Möngke Khan.jpg》——伊利汗国拉施特《史集》抄本细密画。

结果：候选 26 张，逐图过目后 **keep 24 / reject 2**——

- reject：`Yang Shiqi.jpg` 是戴瓜皮帽的黑白照片（晚清民国同名者）；`Gong Zizhen.jpg`
  是据十九世纪照片摹绘的现代炭笔素描。均触「现代影像一律不收」红线。
- keep 里有几件值得点名：朱厚熜《明世宗坐像》轴（清宫旧藏）、旭烈兀与蒙哥的《史集》
  抄本细密画（元帝无传世御容，这两帧是现存最早的域外细密画记录）、
  杨慎幅内自题「明翰林脩撰…楊先生象」并附长跋（昆明建水存三本，此为壬申摹本）、
  洪秀全像出自十九世纪西文报刊雕版（如实注明，非中国传世画像传统）。

**层级改判权下放到审计账本。** 原先中文题名的图档一律落「（明清）佚名舊像」规则、
判 L2 版画，结果孝庄朝服像（清宫旧藏绢本）、秦良玉立轴、唐寅/夏言/严嵩/史可法/
熊廷弼/张廷玉/福康安的纸本容像全被错标成刻本。现 `audit.json` 支持 `tier` 字段
逐件改判（`build-catalog.mjs` 校验合法值），判据是媒材而非题名：
明确纸绢本手绘 → L1；明确刻本/石印/报刊雕版 → L2；媒材判不清 → 保持 L2 并注「版本待考」。
兜底文案也从「（明清）佚名」改为「（明清）佚名舊像（版本待考）」——断代不是著录，
界面原样读出来时不能让读者误以为是比定过的明清作品。

其余 24 位（许衡、刘秉忠、阿合马、张弘范、王保保、韩林儿、陈友谅、明玉珍、杨溥、杨荣、
俞大猷、孙承宗、徐渭、卢象升、李定国、黄宗羲、兆惠、奕訢、岳钟琪、杨秀清、石达开、
丁汝昌、李秀成、邓世昌）在 Commons 无可确证的古代画像，一律 L4 呈现——**不借图充数**。

## 六、交互指南

| 操作 | 效果 |
| --- | --- |
| 点击节点 | 1 度聚焦，非相关节点淡出至 0.12 |
| 再次点击 | 扩展到 2 度 |
| 点击连线 | 「交集详考」：双方摘要、关键史料、关系演变时间轴 |
| `⌘K` / `Ctrl+K` | 全局检索（支持字、号、谥号、庙号、封爵、官职） |
| 寻路 | 任选两点，六度分隔，最多 3 条等长路径 + 共同关系圈 |
| 滚轮 | 以光标为锚点缩放（0.25×–12×），自动切换三级语义 LOD |
| 双击节点 | 镜头直接贴上去（≥3.2×），凑近看清这个人 |
| 触控板捏合 | 与滚轮同源：ctrl+wheel 单独走细步长，捏合即「凑近看细节」 |
| 拖拽 | 平移；画布空白处拖拽即调整视野 |
| 底部时间轴 | 朝代切片、公元双滑块、单年截面（关系边按当年状态变色） |
| 顶栏主题键 | 宣纸日间 ↔ 玄墨夜间 |

**放大这件事是三处联动的，缺一处就「看着放大了、其实什么也看不清」。**
早期版本滚轮上限只有 3.6×，而且节点半径封顶在 1.35×——间距按倍率拉开、圆却纹丝不动，
滚轮滚到底也只是满地芝麻，这就是「放大了却认不出人」。现在的口径：

1. **上限 3.6× → 12×**（`ZOOM_MAX`）。九百人铺开后相邻两人只隔二三十个世界单位，
   12× 下单人才占得上数百像素。
2. **半径按 `1.35·(scale/1.35)^0.62` 次线性生长，3.2 倍封顶**（`nodeRadius`）。
   线性放大会让人像吞掉整屏；次线性「越近长得越慢」，12× 时权重 100 者直径约 140px。
   绘制与命中测试必须共用这一个函数——两处各写一份公式，早晚有一处忘了改，
   表现为「看着点中了却选不中」。
3. **字号随 √(scale/2) 缓慢加成，1.7 倍封顶**。10× 时人像 140px 大、
   名字还是 13.5px，比例失衡；但字号无限制放大又会挤掉标签，故只跟一半。

滚轮监听挂在原生 `addEventListener({ passive: false })` 上：React 委托的 wheel 是被动监听，
`preventDefault()` 只会换来控制台警告；触控板捏合（浏览器发来 ctrl+wheel）
若照常规步长处理，捏一下就把整页放大而画布不动。
缩放能力有专属验收脚本：`node scripts/shots/verify-zoom.mjs`，
往画布打真实滚轮事件、从右上角「缩放 x.xx×」读数取真值，
断言最大倍率 ≥10×、光标锚点处有实体节点、控制台零错误。

### 性能基线（可实测，不是声称）

这一节分两件事，因为它们的可信度完全不同：**布局耗时是纯计算，可以精确复现；帧率受渲染影响，测不准。**

先说布局。`/bench` 页面测的是帧率，但它的 `×N` 做法（把真实分片整体复制若干份、只换 id）
更适合用来压计算量。所以把「布局」单独立成脚本：

```bash
node scripts/bench-layout.mjs --multiply 5 --repeat 3
```

它读真实分片 JSON，合并后直接调 `computeForceLayout`，报出中位耗时——没有浏览器、
没有光栅化、没有头像缓存，量到多少就是算法花了多少。

#### 第一次跑出来的是坏消息

| 倍数 | 节点 / 关系 | 两两精确 O(n²) |
| --- | --- | --- |
| ×1 | 642 / 1,068 | **0.9 s** |
| ×2 | 1,284 / 2,136 | 6.5 – 15.5 s |
| ×3 | 1,926 / 3,204 | **26.2 s** |
| ×5 | 3,210 / 5,340 | **97.6 s** |

×2 一档跑两次得到 6.5 s 与 15.5 s，列成区间——这一档正好卡在 CPU 缓存装得下与装不下的边界上，
没能把波动压到可忽略，如实标出来。

节点涨 5 倍、耗时涨 108 倍，近似 **n^2.9**，比理论上的 n² 还陡。根因有两层：
原实现是 800 轮迭代、每轮对全部节点两两算斥力；节点一多，两个坐标数组装不进 CPU 缓存，
每次访问都是内存往返，单次运算也变贵。

642 人 0.9 秒还无感，一千人以上就开始肉眼可见——**也就是说「继续加人物」这条路当时已经走不通了，
卡住的不是数据量，是算法。**

#### 换成 Barnes-Hut 四叉树

`src/lib/barnes-hut.ts`。思路不是少算几个点，而是换求和方式：把空间递归四等分，
每个格子记下这团点的总质量与质心；对远处一整团，用质心当作一个点代算即可，
判定「够远」用经典准则 `格子边长 / 距离 < θ`，取 θ=0.85（与 d3-force 常用值同量级）。
斥力式仍是 Fruchterman–Reingold 的 `k²/d`，与改造前完全一致——**换算法，不换物理模型**。

| 倍数 | 节点 / 关系 | 改造前 O(n²) | 改造后四叉树 | 提速 |
| --- | --- | --- | --- | --- |
| ×1 | 642 / 1,068 | 0.9 s | **0.43 s** | 2.1× |
| ×2 | 1,284 / 2,136 | 6.5 – 15.5 s | **1.0 s** | 6.5 – 15× |
| ×3 | 1,926 / 3,204 | 26.2 s | **1.40 s** | 19× |
| ×5 | 3,210 / 5,340 | 97.6 s | **2.50 s** | 39× |

节点涨 5 倍、耗时涨 5.8 倍，**这就是 n log n 的样子**。×1 只快 2.1 倍，是因为这个规模下
建树、边力、向心这些 O(n) 的固定开销占比大，算法加速只作用在 n² 那一项上；规模越大越占便宜。

#### 怎么确认「换了算法，但没换图」

快 39 倍是好事，可近似算法若把图算歪了，快也没有意义。所以配了两个对照工具：

```bash
node scripts/compare-layout.mjs        # 出数字
node scripts/shots/layout-ab-shot.mjs  # 出图
```

`compare-layout.mjs` 把同一份数据跑两遍，比抽样节点对在两套坐标下距离的对数相关性、
边的平均长度、最近邻间距；`layout-ab-shot.mjs` 生成两栏同尺度点线图，可目视比对。

| 指标 | 精确 | 四叉树 θ=0.85 | 差异 |
| --- | --- | --- | --- |
| 平均边长 | 20.5 | 20.1 | −1.9% |
| 边长中位数 | 18.2 | 18.3 | +0.3% |
| 最近邻最小值 | 2.9 | 2.4 | −16.6% |
| 距离相关性（对数尺度，2,997 对） | — | — | **r = 0.996** |

**这一步抓到了一个真 bug。** 第一版跑出 r = 0.9796、最近邻间距虚高四成。我起初以为是 θ 太松，
把它从 0.7 调到 1.2，却发现相关性并不单调变好，才回头查物理。问题在质量因子：
FR 的 `k²/d` 是「每一对点各贡献一份」，一团 m 个点对一个点的合力应是 `m·k²/d`；
四叉树把整团压成质心时若漏乘 m，远处的大团就被当成一个人来推——不是「稍微不准」，
而是**人数越多的地方斥力反而越不涨**。补上后再测，r 从 0.98 升到 0.996，
平均边长差异从 +7.5% 收到 −1.9%。

这类错误跑得通、图看着也还行，只有拿两套结果对一遍才露馅——所以这两个脚本留在仓库里，
不是一次性的验证工具。

#### 785 人时 r 掉到 0.98，这不是回归

第六片（宋元明清）建完，同一套对照脚本在全量 785 人上给出：

| 指标 | 精确 | 四叉树 θ=0.85 | 差异 |
| --- | --- | --- | --- |
| 平均边长 | 11.3 | 11.2 | −0.7% |
| 边长中位数 | 9.1 | 9.1 | −0.3% |
| 最近邻中位数 | 4.0 | 4.0 | +1.1% |
| 包围盒 | x ±800 / y ±68 | x ±800 / y ±68 | 一致 |
| 距离相关性（2,997 对） | — | — | **r = 0.9818** |

与 642 人时的 r = 0.9960 相比确实退了，但**四条形状指标全部在 1% 以内、包围盒逐位相同**，
所以这不是算法退步，而是度量本身随规模变敏感：抽样对数固定为 2,997 对，
人一多，落在簇心密集处的点对占比就上升，而那里边长只有 3–5 个单位，
在**对数尺度**上挪 1 个单位就是两成偏差。同一份图缩小看，这种误差不可见。

因此验收判据不写成「r ≥ 0.99」这一条，而是三条一起看：
**平均边长与中位数偏差 < 2%、最近邻中位数偏差 < 2%、包围盒一致**，r 只作旁证。
把 r 当硬阈值，只会逼着后来的人去调 θ 或改抽样，把「图变没变」这个真问题糊弄过去。

顺带一个交叉验证：第二批扩容时曾在浏览器里于 444 人基准上测到 ×7 = 3,108 人 / 89.4 s，
与脚本在 642 人基准上测到的 3,210 人 / 97.6 s 同量级。两条独立路径、不同运行时给出同一个数，
说明改造前的那个「一分半」不是某处实现的怪癖，而是算法本身的账。

#### 877 人：平均边长差 2.8%，以及为什么不该去调 θ

八片齐备后再跑一次对照，全量 877 人 / 1,397 边：

| 指标 | 精确 O(n²) | 四叉树 θ=0.85 | 差异 |
| --- | --- | --- | --- |
| 布局耗时 | 3,021 ms | 624 ms | −79.3% |
| 平均边长 | 7.9 | 7.7 | **−2.8%** |
| 边长中位数 | 4.9 | 4.9 | −0.2% |
| 最近邻中位数 | 2.4 | 2.4 | +0.7% |
| 包围盒 | x ±800 / y ±61 | x ±800 / y ±61 | 一致 |
| 距离相关性（2,996 对） | — | — | **r = 0.9963** |

平均边长 −2.8%，越过了上面那条 2% 的红线，所以如实记在这里。它是不是「近似太松」？
我用收紧 θ 的办法验了一遍，结论是**不是**：

| θ | 耗时 | 平均边长 | 边长中位数 | 最近邻中位数 | r |
| --- | --- | --- | --- | --- | --- |
| 0.85（现用） | 624 ms | −2.8% | −0.2% | +0.7% | **0.9963** |
| 0.60 | 804 ms | −0.4% | **+4.3%** | +1.4% | 0.9941 |

θ 收紧到 0.6 后，平均边长确实回到 −0.4%，代价是多花 29% 的时间，却把**边长中位数推到 +4.3%**、
r 反而降到 0.9941。也就是说误差没被消除，只是从一条指标搬到另一条上。
这正是「三条一起看、r 只作旁证」的原因：**任何单条指标都能被调参喂饱**，
只有三条同时收敛才说明图真的没变。877 人这档：两条主指标（中位数、最近邻）都在 0.7% 内、
包围盒逐位相同、r 是三个规模里最高的，所以仍按 θ=0.85 出厂，
把 −2.8% 这个数写在这里供复核，不拿它去换一个更慢且更偏的解。

至于帧率，我仍然没能测准，如实说明原因：同一档位连测两次会得到两个差三倍的值，
×1 首测 123.8 FPS（8.9 ms/帧）、复测 36.5 FPS（27 ms/帧），重载页面后首测仍是 123.8，稳定复现。
1440×900 软件光栅化下，每帧画两百来个节点（含头像 `drawImage`）与近千条边只花 8.9 ms 不太可能，
27 ms 才是合理量级——所以我倾向认为**首测量到的是画布尚未进入「流光持续重绘」的空转帧**，
复测值才作数。但我没能确证根因（`animating` 判定读的是 props ref，理论上首测也该在重绘），
故此处不把 36.5 当作定论，只记下「同一页面内首测偏高、复测稳定」这条实测事实。
顺带一提，×3 的 50.4 FPS 反而高于 ×1 的 36.5，与此不符，同样未查明。

**已排除的解释**：不是画像数量的问题。画像从 158 幅增至 444 幅后帧率确有下降，
但屏内 201 节点（804 条边视角）比扩容前的 246 节点更慢，说明成本跟着边数走——
边从 495 增至 781（1.58 倍），帧率 67.5 → 36.5（降 46%），量级大致对得上。

至于画布本身靠什么撑住这个密度，是下面三条设计与一处过绘保护：

* 单画布手动投影（不做 DOM 节点）、屏幕空间算几何（无需 `ctx.scale` 重排）；
* 视口外扩 120px 裁剪 + 三级语义 LOD，宏观层连弱关系边都不画；
* 头像走离屏位图缓存——直接逐帧 `drawImage` 一张 SVG 要重新栅格化，五百人时单这一项
  就能吃掉两百多毫秒；
* **过绘保护**：一屏超过 380 人时，只给权重 70 以上者保留头像、权重 55 以上者标名，
  并省掉帝王光晕。那个密度下每个人的五官和姓名都只有米粒大，画了也认不出，
  余下的算力不如留给帧率。

#### 两处「看着像没画」的真故障

第六片上线后，验收截图里出现两种「空白」，一开始都被我当成相机没适配或图片没下载完，
后来查明是两个独立的真 bug，与相机、与图源都无关：

1. **画像解码完成时没人通知画布。** `portrait-resolver` 早就实现了 `onPortraitLoaded`
   这个订阅口，但**画布从来没订阅过它**——图片 `onload` 不碰 `dirtyRef`，主循环在入场动画
   结束后就靠 dirty 驱动。结果是：首帧没赶上加载的那几十张图，永远是空圆环，
   要等用户随手动一下鼠标（悬浮、拖拽、滚轮）才补上。785 人首屏同时有几十张图在解码，
   撞上几乎是必然，所以看到的是「若干空白圆圈」而不是全空。
   修法是订阅后置 dirty，让图片到位就重绘。
2. **入场动画用墙钟判断「还要不要继续画」。** 原来的条件是 `now - introRef < 1000`。
   浏览器会把 `requestAnimationFrame` 节流到 0 Hz（切后台标签、窗口被遮挡、无头截图都会）。
   那一秒里若一帧都没有，等下一帧到来时墙钟条件早已过期，而 dirty 又是 false，
   于是**再也不会重绘**：画布永久停在入场动画的第一帧上，而每个节点都因 `appear <= 0`
   被 `continue` 跳过——看起来就是一张近乎空白的画布。修法是不再问墙钟，
   改由绘制自己置位 `introDoneRef`：只要还没画到 `intro >= 1`，循环就一直要求重绘，
   帧被节流多久都不怕，下一帧一来直接跳到终态。

配套把 `scripts/shots/expansion-shot.mjs` 从「睡 3 秒再拍」改成
**等 `canvas[data-intro="done"]` 且墨量过阈值**，空白就直接抛错。固定 sleep 的问题是
它既不能证明拍到了什么，也不能在拍到坏图时报警——上面那张「切分片后全空」的截图，
就是在这种「脚本永远说 pass」的状态下混进验收的。

复测脚本：`node scripts/shots/bench-clean.mjs`（每档重载页面，避免会话内累积影响）。
